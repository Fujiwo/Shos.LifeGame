# 新しい高速化オプション 提案書

- 作成日: 2026-10-14
- 対象: `Shos.LifeGame/ShosLifeGame.h`（一部は `Shos.LifeGame/Shos.LifeGame.cpp`）
- 範囲: 既存の 4 オプション（`USEBITS` / `FAST` / `MT` / `AREA`）に加える、新しい `#define` オプションの提案
- 関連: [既存コード高速化 計画書](2026-10-14_SpeedupPlan.md)

## 1. 目的

既存の 4 オプションと同じく「1 つ有効にすると、こういう理由で速くなる」と説明できる高速化手法を、新しいオプションとして追加する。この文書では候補を挙げて比較し、採用する順番を提案する。

## 2. 候補の一覧

| オプション | 手法 | 期待できる効果 | 実装の規模 | 前提となるオプション | 推奨 |
|-----------|------|---------------|-----------|---------------------|------|
| `SWAR` | 64 ビットのワード単位でビット並列に計算する | 大（現状の数十倍の見込み） | 中 | `USEBITS` | ◎ 最優先 |
| `TILE` | 変化のあったタイルの周辺だけを計算する | 盤面次第で大 | 中〜大 | `AREA` | ◎ |
| `FRAMESKIP` | 計算と描画の頻度を切り離す | 描画が律速のとき大 | 小 | なし（Win32 側） | ○ |
| `LUT` | 近傍パターンの表引きで計算する | 中 | 小〜中 | `USEBITS` | △ 教材向け |
| `SIMD` | `SWAR` を AVX2 の 256 ビットに広げる | `SWAR` 比で 2〜4 倍 | 中 | `SWAR` | ○ `SWAR` の後 |
| `GPU` | Direct3D 11 の Compute Shader で計算する | ボードが大きいとき大 | 大 | なし | × 見送り |
| `HASHLIFE` | Gosper の HashLife | 周期的な巨大パターンで桁違い | 大 | なし | × 別実装として扱う |

## 3. 各候補の詳細

### 3.1 `SWAR`（SIMD Within A Register）

**概要**: 1 ワード（64 ビット）に並んだ 64 セルの次の世代を、ビット演算だけでまとめて求める。

**仕組み**

1. 上・中・下の 3 行それぞれから、対象のワードとその左右のワードを読む。
2. シフトと OR で「左隣のセル」「右隣のセル」を表すワードを作る。これで、隣接 8 方向のそれぞれに対応する 8 個のワードがそろう。
3. 8 個のワードを、半加算器・全加算器を組み合わせたビット論理で足し合わせる。各ビット位置の近傍数が、3 ビットの 2 進数（bit-sliced な表現）で得られる。
4. 「近傍数が 3」または「近傍数が 2 かつ生存」を論理式で求め、64 セル分の次の世代を 1 ワードで得る。

**現在の格納形式との関係**

- 現在の `BitCellSet` は、`UnitInteger`（= `Byte`）単位の MSB-first（左端のセルが最上位ビット）で、行のバイト数は WORD 境界に揃っている（`GetRowByteNumber`）。これは `CreateBitmapIndirect` が要求する形式に合わせたものである。
- 64 ビットで読み込むと、リトルエンディアンの CPU ではバイトの順序が逆になる。読み込み時にバイトスワップ（MSVC は `_byteswap_uint64`、g++ は `__builtin_bswap64`）をすれば、左端のセルが最上位ビットになり、シフトの向きが素直になる。
- 行のバイト数を 8 の倍数に揃えると、行の末尾をまたぐ読み込みがなくなり、処理が簡単になる。8 の倍数は偶数なので、`CreateBitmapIndirect` の WORD 境界の条件も満たす。ただし、回帰テストの `BitmapRowIsWordAlignedPackedBits` が行のバイト数を厳密に確認している場合は、`SWAR` 有効時の期待値を分ける。

**他のオプションとの関係**

- `USEBITS` が必須。`USEBITS` なしで `SWAR` を定義したら `#error` にする。
- `FAST` の直接ループを置き換えるので、`FAST` の有無は問わない。
- `MT`: 行単位で分割するので、そのまま組み合わせられる。
- `AREA`: area の左右の端をワード境界に切り下げ・切り上げて計算する。area の集計は、ワードが 0 でないときだけ `std::countl_zero` と `std::countr_zero`（C++20 の `<bit>`）で端のセルを求める。

**期待できる効果**: 1 セルあたりの演算が約 1/64 になる。メモリアクセスもワード単位になるので、1000×1000 のランダムな盤面では現状の数十倍の速さが見込める。

### 3.2 `TILE`（タイル単位の変化追跡）

**概要**: ボードを固定サイズのタイル（例: 64×64）に分ける。前の世代で変化があったタイルと、その周囲 8 タイルだけを計算する。

**背景**: 現在の `AREA` は、生存セル全体の外接矩形しか持たない。パターンがボードの離れた 2 か所にあると、矩形はほぼボード全体に広がる。静止物（ブロックなど）や振動子が散らばった盤面でも、毎世代すべてを計算し直している。

**仕組み**

- タイルごとに「前の世代から変化したか」のフラグを持つ。
- 自分と周囲 8 タイルがどれも変化していなければ、そのタイルの次の世代は今の世代と同じなので、計算を省く。
- **二重バッファに関する注意**: `Game` は `mainBoard` と `subBoard` を毎世代入れ替える。計算を省いたタイルでも、`subBoard` 側には 2 世代前の内容が残っている。そのため「省いたタイルは `mainBoard` から `subBoard` へコピーする」か「2 世代続けて変化がなかったタイルだけを省く」のどちらかが必要になる。実装を簡単にするなら前者、速さを優先するなら後者。

**他のオプションとの関係**

- `AREA` の発展形として、`AREA` を必須とする。外接矩形の area は、タイルの集合から求めて、描画や既存テストとの互換を保つ。
- タイルの幅を 64 にすると、`SWAR` のワードと一致し、組み合わせやすい。
- `MT`: 計算対象のタイルをスレッドに振り分ける。

**期待できる効果**: ランダムな盤面の初期段階では、ほぼ全タイルが変化するので効果はない。数百世代が過ぎて静止物と振動子が中心になった盤面や、グライダー銃のように局所的に動くパターンでは、計算量が大きく減る。

### 3.3 `FRAMESKIP`（計算と描画の分離）

**概要**: 計算を描画の頻度から切り離す。描画は一定間隔（例: 60fps）にとどめ、その間に計算できるだけの世代を進める。

**仕組み**

- `Shos.LifeGame.cpp` の `MainWindow::Next` で、前回の描画から 1/60 秒経っていなければ `Invalidate` と `SetTitle` を呼ばずに次の世代へ進む。
- `ShosLifeGame.h` は変更しない。Win32 側のオプションとして、`ShosWin32.h` の `IDLE` や `TIMER` と同じ場所で定義する。

**注意点**

- タイトルに表示している FPS は「世代数 / 経過時間」で求めているので、値は「1 秒あたりの世代数」の意味のまま変わらない。ただし「1 秒あたりの描画回数」ではなくなるので、README の説明を合わせて直す。
- 計算が十分速くなった後（`SWAR` 導入後など）ほど、描画が律速になるので効果が大きくなる。

### 3.4 `LUT`（ルックアップテーブル）

**概要**: 近傍の状態をビット列としてまとめ、表を引いて次の世代を求める。

**仕組みの例**: 横 4 セル × 縦 3 行の 12 ビットを添字にして、中央 2 セルの次の状態（2 ビット）を引く。表は 4096 エントリで、L1 キャッシュに収まる。

**位置付け**: `SWAR` より実装が簡単で、効果は `FAST` と `SWAR` の中間程度と見込まれる。`SWAR` を採用するなら、速さの面で `LUT` を追加する意味は薄い。「表引きによる高速化」という教材としての段階を示したい場合に限って採用する。

### 3.5 `SIMD`（AVX2）

**概要**: `SWAR` と同じ論理を、AVX2 の 256 ビットレジスタ（`__m256i`）で 256 セルずつ実行する。

**注意点**

- `SWAR` を必須とする。加算器の論理は共通にし、ワードの型と読み書きだけを差し替える形にする。
- AVX2 に対応していない CPU では動かない。MSVC では `/arch:AVX2` が必要になる。
- 1000×1000 では 1 行が 1000 ビット（約 4 ワード分の 256 ビット）しかなく、行の端の処理の割合が大きい。効果は `SWAR` 比で 2〜4 倍程度と見込まれる。

### 3.6 `GPU`（見送り）

Direct3D 11 の Compute Shader で、1 スレッドに 1 セル（または 1 ワード）を割り当てて計算する。

見送る理由は次のとおり。

- 1000×1000 程度では、GPU とのデータ転送と同期のオーバーヘッドが計算時間と同じくらいになる。
- Windows 専用になるので、Linux の回帰テスト（GitHub Actions）で検証できない。
- 依存するライブラリとコード量が、既存のオプションに比べて大きすぎる。

### 3.7 `HASHLIFE`（別実装として扱う）

Gosper の HashLife は、四分木と、部分盤面の未来をキャッシュするメモ化で、周期的なパターンを桁違いの速さで進める。

`#define` オプションに向かない理由は次のとおり。

- データ構造が `Board`（2 次元配列）とまったく異なる。`GetBits` で描画用のビット列を作るには、四分木からの展開が毎回必要になる。
- 1 回の `Next` で 2 のべき乗の世代を進めるのが本来の使い方なので、「1 世代ずつ進めて描画する」というこのプログラムの構造と合わない。
- ランダムな盤面ではキャッシュがほとんど当たらず、むしろ遅い。

扱うとしたら、別のプロジェクト（例: `Shos.LifeGame.HashLife`）として作るのが適切である。

## 4. 採用の順番（提案）

1. **既存コード高速化 計画書の Step 0（ベンチマーク）を先に済ませる。** 各オプションの効果を同じ条件で比べるため。
2. **`SWAR`**: 効果が最も大きい。計画書の Step 1・2（近傍カウントの改善、バイト単位の書き込み）とは、`SWAR` 有効時に置き換えられる関係にある。計画書の Step 1・2 を先にやるか、`SWAR` を先にやるかは、教材として両方の段階を見せたいかどうかで決める。
3. **`FRAMESKIP`**: 実装が小さい。`SWAR` で計算が速くなると描画が律速になるので、`SWAR` の直後に入れると効果がわかりやすい。
4. **`TILE`**: 盤面によって効果が大きく変わるので、Step 0 のベンチマークに静止物の多い盤面のケースを加えてから着手する。
5. **`SIMD`**: `SWAR` が安定してから、必要に応じて着手する。
6. **`LUT`**: 教材としての段階が必要な場合だけ着手する。

## 5. テストの体制への影響

- `Shos.LifeGame.Test/run_regression_tests.sh` は、4 オプションを 0〜15 のビットマスクで列挙している。オプションが増えると組み合わせが 2 のべき乗で増えるので、次のように変える。
  - オプションの一覧と、依存関係（`SWAR` → `USEBITS`、`SIMD` → `SWAR`、`TILE` → `AREA`）をスクリプト内に持ち、無効な組み合わせは除外する。
  - 依存関係を満たさない組み合わせは、ヘッダー側で `#error` にして、ビルドで確実に検出できるようにする。
- `SWAR`、`SIMD` を検証するテストケースを追加する。
  - ボードの幅が 64 の倍数でないもの、64 ちょうどのもの、64 未満のもの
  - ワードの境界をまたいで動くグライダー
- `TILE` を検証するテストケースを追加する。
  - タイルの境界をまたいで動くグライダー
  - 静止物だけの盤面で、何世代進めても結果が変わらないこと
  - 二重バッファの入れ替え後も、計算を省いたタイルの内容が正しいこと
- `SIMD` は GitHub Actions の実行環境で AVX2 が使えることを前提にする。使えない場合はテストを飛ばす仕組みを入れる。
- `GetConfiguration`（回帰テストの出力の先頭に表示する構成名）に、新しいオプションを加える。

## 6. 決めておくこと

- 教材として、既存コード高速化 計画書の Step 1・2 と `SWAR` の両方を段階として残すか
- `SWAR` 有効時に、行のバイト数を 8 の倍数に変えてよいか（変えると `BitmapRowIsWordAlignedPackedBits` の期待値に影響する）
- `TILE` のタイルの大きさ（64×64 を想定）と、二重バッファの扱い（コピーするか、2 世代続けて変化がないタイルだけを省くか）
- `FRAMESKIP` を有効にしたときの、タイトルの FPS 表示の意味と README の書き方
