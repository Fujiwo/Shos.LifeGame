# 原稿向けチェックリスト

stop-ai-slop-jp のクイックチェックから、書籍・記事の原稿に合わない項目を外し(`conflict-resolutions.md` の裁定に基づく)、fujiwo-style 7節・japanese-tech-writing・natural-japanese `doctypes/book.md` の品質基準と、yomiyasu の意味保持の点検を足したもの。上から順に見る。**上位の項目を直さずに下位だけ直しても AI 臭は残る。**

各項目で見つけた問題は台帳に一行ずつ起こし、「直した」か「残す(理由)」を書く。

## 1. 立場(最優先)

- [ ] この章で Fujiwo が引き受けて言い切っている主張が、一文で言えるか
- [ ] その主張に「いや、そうではないだろう」と反論できる具体があるか。「重要だ」「本質的だ」で終わっている段落がないか
- [ ] 「○○もあり、△△もあります」「ケースバイケース」で判断を放棄している箇所がないか。設計判断に唯一の正解がない箇所は、放棄ではなく「ここは目的次第で決まる。筆者は〜を選ぶ」と明示ラベルで書けているか(natural-japanese 第10条)
- [ ] 各節末に、内容の薄い免責(「もちろん例外はある」「状況によって異なる」)を儀式的に置いていないか
- [ ] 評価の場面(選択肢の比較、ツールの使い勝手)に中間温度(「悪くない」「まあまあ」「ここは微妙だ」)があるか。全部を「重要」「強力」にしていないか(裁定 #12)

## 2. 論証の厳密さ(japanese-tech-writing)

- [ ] 推量・伝聞(「かもしれない」「だろう」「ようだ」)を、根拠なく機械的に断定へ変えていないか。事実未確認・読者の疑念・反実仮想を表す文は、不確実性を残したままか(本文内の根拠で確定している場合だけ断定に直す)
- [ ] 異なるもの(別々の決定、別々の原因、種類の違う問題)を一括りの言葉でまとめていないか。腑分けできるか確認する
- [ ] 複数の要因がある事象を、単一の原因に還元していないか。どの要因がどれを説明するのか対応づけられているか
- [ ] 章・節をまたいで、同じ概念の扱い(分類・定義・用語の地位)が一致しているか。ある節で「人間が決める」としたものを、別の節で違う言い方にしていないか
- [ ] 因果を主張する文に、機構(なぜそうなるのか)が一文添えられているか。「AだとBになる」で理由を省略していないか
- [ ] 検出・保証・解決を「必ず」できるかのように書いていないか。条件付きで正確か(「〜しやすい」「〜が成り立つときに限り」)
- [ ] 挙げた例が、主張の全体を実際に支えているか。例が一部しか支えないなら、主張の範囲を狭めているか
- [ ] 「後の章で扱う」「次節で扱う」と前方に逃がした論点は、実際にそこで回収されているか
- [ ] 「ただし」「とはいえ」で譲歩したあと、論を進めずに宙吊りで終えていないか
- [ ] 節の中心となる語を、定義・対象範囲を述べる前に使い始めていないか

## 3. 主体性(false agency・翻訳調の比喩と擬人化)

- [ ] モノが主語で人間の動詞をしていないか。「文化が醸成される」「設計が語る」「コードが教えてくれる」「課題が浮き彫りになる」→ 原文や提供文脈で確定した主体や処理で書き直す(本論にも適用。裁定 #5・#27)。自然なシステム動作は残し、未知の動作主は作らない
- [ ] 「多くの開発者は」「人々は」「現代のソフトウェア開発において」で、自分の経験を一般化していないか。具体的な人・失敗・数値・固有名詞に降りているか
- [ ] 翻訳調の動詞(「示している」「物語っている」「収斂する」「指している」)を多用していないか
- [ ] 英語慣用句の直訳になっていないか(carry→「運ぶ」、open question→「開かれた問い」、expose→「露出する」、live in→「住んでいる」)。字義どおりの動作を想像できてしまう述語は、動作の主体と対象を具体語に言い直す(japanese-tech-writing)
- [ ] 無生物主語の他動詞文を直輸入していないか(「モデルは〜を知っている」「データが語るのは」)。人か処理を主体に戻すか、「〜から分かる」「〜に含まれる」に言い直す
- [ ] 研究者の話し言葉(「効く」「刺さる」「筋がいい」)を書き言葉に混ぜていないか。効果・見込みの内容を具体的に書く
- [ ] 自称(「筆者」か「私」か)を1つの原稿の中で混ぜていないか。プロファイルの指定に合わせる(裁定 #4)

## 4. 読み手の負荷管理(japanese-tech-writing)

- [ ] 読者が一度に保持する情報を、一段ずつ増やしているか。段落を削ったとき、他で使われなくなった主題を残していないか
- [ ] 後で参照しない固有名(変数名、関数名、ファイル名)をそのまま出していないか。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済むか
- [ ] 概念を初めて示す文で、読者がまずその概念の種類(データ構造、手順、制約など)を読み取れる順序になっているか。未習の読者向けの性質・仕組みを、種類の同定より前に置いていないか
- [ ] 新しい例を追加するとき、前の例と何が違うのか、なぜもう一つ必要なのかを前置きしているか
- [ ] 「あなた」と読者を二人称で呼んでいないか。論証中は役割名(「開発者」「読者」)で書き、二人称は場面への導入・章や本の結びなど限られた要所に留める(裁定 #5 と整合)

### 局所的な読みやすさと意味保持(yomiyasu)

- [ ] 主語と述語、修飾語と掛かり先、指示語と対象を順読みで追えるか。関係が明確な箇所は残し、不明な関係を推測で確定していないか
- [ ] 助詞・語順・接続・文の分割や結合を変えた箇所で、主体と対象、条件・例外・否定・数量・因果・時系列の範囲が同じか
- [ ] 修正前後の「主張・比重・言い切りの強さ・文の働き」を保ったか。評価を目的、説明を勧め、実施済みの変更を予定に変えていないか(裁定 #22・#26)
- [ ] 著者承認済みの内容変更と読みやすさの修正を区別し、承認済みの内容を比較基準にしたか。提供素材にない主体・原因・条件を足していないか
- [ ] 文長・読点数・漢字割合・箇条書き比率だけで自然な文を変えていないか。専門用語・識別子・著者の軽口を一般語へ薄めていないか(裁定 #23・#24・#27)

## 5. 構造のテンプレ

- [ ] 序文が「決めつけ→反転」(「〜と思われがちだ。しかし実は〜」)の型になっていないか。なっていても1章に1回まで
- [ ] 全段落の長さが 3〜5 文に揃っていないか。段落の長さ・密度・結論の有無にムラがあるか
- [ ] 「体験→引用→抽象化」「問い→整理→まとめ」の同じ節構成が3節以上続いていないか(natural-japanese 第8条)
- [ ] 同じ形の文末が4文以上連続していないか。連続している箇所だけ崩す。常体基調なら「〜である。」「〜のである。」を「〜する。」「〜と考えてよい。」「なぜか。」などに、敬体基調なら「〜です。」「〜ます。」を「〜します。」「〜と考えてかまいません。」「なぜでしょうか。」などに崩す(fujiwo-style 4節 型D。全部をばらけさせようとしない)
- [ ] (敬体基調のとき)文末を散らすために、検証済みの事実を「〜でしょう。」「〜と言えるでしょう。」で弱めていないか。「〜のです。」が続いて説教調になっていないか(fujiwo-style 4節 型D)
- [ ] 定義文の型(「Xとは〜である」)を3回連続で使っていないか。「括弧で挟む」「使ったあとで名づける」「例を見せてから名づける」を混ぜているか(book.md)
- [ ] 抽象的な原則の前に、具体例(コード、図、身近な比喩)が置かれているか。定義から入って後から例を出す順序になっていないか
- [ ] 「AではなくB」「単なるAではなくB」が、本当の誤解訂正以外で使われていないか。強調のためだけなら直接 B を書く(裁定 #11。一律置換はしない)
- [ ] 「Aでもない、Bでもない、Cだ」の否定的列挙、「シンプル。それだけ。それが本質。」の劇的な断片化を使っていないか
- [ ] 地の文で根拠なく「3つのポイント」「3つの観点」と並べていないか。2つか1つに削れないか(名前のついた列挙と定型部は対象外。裁定 #6)
- [ ] 本文の説明を箇条書きに逃がしていないか。箇条書きは真に並列な圧縮のみ(定型部は対象外。裁定 #13)

## 6. 語彙

- [ ] AI 偏愛語(泥臭さ、手触り、解像度、熱量、本質、思想、営み、文脈、装置)を1章に複数撒いていないか。特に「本質」「営み」は既存原稿で目立つ。1章に各1回までを目安にし、それ以上は具体語に置き換える
- [ ] 必殺技造語(真理、虚飾、禁欲的、美学、境地、結末)で個人の経験を膨らませていないか
- [ ] 比喩的な横文字(「思考の OS」「マインドセットをアップデート」「人生をハック」)を撒いていないか。技術用語のカタカナ(クラス、メソッド、リファクタリング)は戻さない(裁定 #15)
- [ ] 副詞(「非常に」「極めて」「かなり」「まさに」)を1段落に2個以上重ねていないか
- [ ] 「〜すぎる」を1章に3回以上使っていないか
- [ ] LLM っぽい空句(japanese-tech-writing)を使っていないか。**予告と総括**(「重要なのは〜である」「本章では〜を扱う/探求する」「まとめると」「要するに」)、**正面から系**(「正面から扱う/回収する」)、**空虚な形容**(「不可欠」「核心的」「鍵となる」「多角的」「包括的」)、**空虚な動詞**(「掘り下げる」「深掘りする」「言語化する」)、**接続の型**(「〜という側面から」「さらに」「また」「加えて」の連打)。中身の代わりに姿勢だけを宣言していないか
- [ ] 「〜することができる」→「〜できる」など、意味を保つ簡潔化ができるか(natural-japanese `forbidden-patterns.md`)。「〜と言えるだろう」「〜かもしれない」は2節(論証の厳密さ)で判断し、読みやすさだけの修正では強さを変えない。内容の訂正が必要なら別の確認事項にする(裁定 #22)
- [ ] 新出の専門用語・略語に、初出の一文で「名前(一言説明)」が添えられているか。既出でも間を空けて再登場する箇所に、一言の思い出させがあるか(fujiwo-style 3節 例外規定、book.md)
- [ ] 硬い接続詞(「しかしながら」「したがって」「ゆえに」)を多用していないか。「また」「そして」「例えば」「但し」「一方」「そこで」が中心か(fujiwo-style 3節)
- [ ] 断定している記述は検証済みか。未確定・未検証の事項だけ「〜のようだ」「〜と思われる」になっているか。検証済みの事実に伝聞を混ぜていないか(裁定 #2)

## 7. 記号・表記(fujiwo-style 3節が唯一の基準。裁定 #7)

- [ ] 全角 `（）` `！` `？` `．` `，` を使っていないか(半角 `()` `!` `?` と `。` `、` に)
- [ ] 全角ラテン文字・全角数字を使っていないか
- [ ] 全角ダッシュ `──` `—` が混入していないか(読点・改行・コロンに)
- [ ] 「」を固有の呼称・初出の用語名・直接引用以外(普通の形容詞や心情)に使っていないか。書名・パターン名は『』(裁定 #8)
- [ ] `**` 太字は、初出の用語(無制限)と、節あたり1、2箇所までの強調だけか。同じ用語を2回以上太字にしていないか(裁定 #9・#17)
- [ ] `**` の残骸(閉じ忘れ、空の `****`)がないか
- [ ] 補助lintが太字の表示を指摘した場合、実際の表示を確認してから、意味と強調範囲を保つ修正を選んだか(裁定 #24)
- [ ] 絵文字を使っていないか(fujiwo-style: 観測 0 件)
- [ ] 1文に3項目以上を中黒「・」で並べていないか(「と」「や」への置換を検討。禁止ではない)
- [ ] 角括弧 `[]` を本文中で使っていないか(リンク記法は除く)
- [ ] リンク・出典・注記の書式が、プロファイルの規定どおりか。紙の書籍を含む媒体では、リンク先を紙面でもたどれる書き方になっているか
- [ ] 注記は `※` で本文から分離されているか

## 8. プロジェクト固有(執筆プロファイル + fujiwo-style 7節 + book.md)

- [ ] 見出しの文言・プロファイルが定める見出しタグ・章の定型部の文言を変えていないか(裁定 #1)
- [ ] 地の文(段落本文)が採った基調に揃っているか(裁定 #21)。常体基調なら、敬体が導入・結び・節の冒頭の呼びかけ以外に紛れていないか。敬体基調なら、常体の文や体言止めが段落本文に紛れていないか(箇条書き・表・手順ステップは除く)。定型部や注記など要素ごとの文体は、プロファイルの指定に揃っているか
- [ ] 章の冒頭で、この章を読むと何ができるようになるかが一言で示されているか
- [ ] 前章までとの橋渡し、章末の要約と次章への接続があるか
- [ ] コード例の直前に前提(言語、対象バージョン、必要なパッケージ)が地の文で示されているか(fujiwo-style 4節)
- [ ] Fujiwo 流の軽口・脱線・言い切りを「不要」として削っていないか(裁定 #3。具体例はプロファイル)。**削る前に「これは Fujiwo の声か、AI の水増しか」を問う**
- [ ] プロファイルが定める章の定型部以外の本論で、修辞的な溜め(「ここには〜が潜んでいる」)や決め台詞での演出をしていないか(裁定 #19。定型部は対象外)
- [ ] プロファイルのプロジェクト固有のチェック項目(コード・図版・書式・禁止事項など)を回したか

## 9. 最終パス

- [ ] 声に出して読むつもりで通読し、息が続かない箇所、読点を打ちたい箇所、リズムが揃いすぎている箇所を見た
- [ ] 台帳に「残す(理由)」の行がある(「直した」だけの台帳は、一律修正の疑いがある。裁定 #10)
- [ ] 補助lint・diffの候補を既存の台帳に統合し、警告ゼロを意味保持の保証にしていないか。意味を保つ案が得られない箇所は残すか著者確認にしたか(裁定 #22・#29)
- [ ] プロファイルの検証コマンドを実行した
- [ ] 今回作成した中間ファイル(台帳、lint の JSON、バックアップ、意味保持の比較用ファイル)を削除した
