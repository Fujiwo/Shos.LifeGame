# 他の執筆プロジェクトで使うための手順書

`fujiwo-manuscript-voice` を、別の書籍や記事の執筆プロジェクトに導入する手順。スキル本体にはプロジェクト固有の約束事を書かない設計なので、導入先で行うのは「スキルをコピーする」「執筆プロファイルを書く」「指示ファイルからプロファイルを指す」の3つである。

## 1. 導入するもの

次の6つのスキルを、フォルダーごとそろえてコピーする。`fujiwo-manuscript-voice` は中核4スキルと補助スキルを `../<スキル名>/` の相対パスで読むので、6つを同じ親フォルダーの下に並べる。1つでも欠けると動かない。

| スキル | 役割 |
|---|---|
| `fujiwo-manuscript-voice` | 入口。中核4スキルと補助スキルの読む順序・適用工程・裁定を固定する |
| `fujiwo-style` | Fujiwo 本人の表記・語尾・構成の実測ルール(最終権限) |
| `japanese-tech-writing` | 段落構成・論証の厳密さの規範 |
| `natural-japanese` | 工程と読みやすさ。lint などのスクリプトを含む |
| `stop-ai-slop-jp` | AI臭の検査観点 |
| `yomiyasu` | 局所的な推敲と意味保持の点検。lint・diffのスクリプトを含む |

各スキルの `scripts/__pycache__/` は Python の実行時キャッシュなので、コピーしなくてよい。

## 2. 置き場所

使うツールに合わせて置く。

- **Claude Code**: プロジェクトの `.claude/skills/<スキル名>/`。複数のプロジェクトで共有するなら、ユーザー単位の `~/.claude/skills/<スキル名>/` に置いてもよい。
- **GitHub Copilot**: プロジェクトの `.github/skills/<スキル名>/`(このスキルの配布元のリポジトリと同じ配置)。
- **両方を使う**: 両方に置き、どちらを正とするかを決めて、もう一方を同期する(配布元のリポジトリでは `.github/` を正とし、`sync-copilot-to-claude` で `.claude/` に反映している)。

スキル本文の中のコマンドは、スキルディレクトリを `<skills>` と書いている(例: `SKILL.md` 3-3節の `python <skills>/natural-japanese/scripts/lint.py`)。`.github/skills`、`.claude/skills`、ユーザー単位の場所など、実際の置き場所に読み替えて実行する。

## 3. 実行環境

`natural-japanese` の lint を使うには、次が要る。

- Python 3
- `sudachipy` と `sudachidict_core`(`python -m pip install sudachipy sudachidict-core`)
- Windows では、実行前に `PYTHONUTF8=1` を設定する。設定しないと、日本語のパスや出力の文字コードで失敗する。

`natural-japanese` の診断を `exp` の深さで行うときだけ、追加で torch と約1GBのモデルのダウンロードが要る。通常の `write` / `revise` / `audit` では要らない。

`yomiyasu` のlint・diffは Python 3 の標準ライブラリで動く。実行条件と比較基準は `yomiyasu-integration.md` に従う。警告ゼロは意味保持の保証ではない。

## 4. 執筆プロファイルを書く

プロジェクトのルートに `執筆プロファイル.md` を作る。ひな形は `profile-template.md`(このファイルと同じフォルダー)にある。

書き方の要点:

- **確定していることだけを書く。** 空欄のままの項目は、スキルが既定の扱い(`../SKILL.md` 0節「プロファイルがないとき」)に倒すか、依頼者に確認する。推測で埋めると、推測がそのまま規則になる。
- **文体の基調は必ず決める。** 書かなければ常体基調になる(fujiwo-style 4節 型Dの既定)。敬体にしたい場合は、地の文だけでなく、定型部(リード、章の結論など)と注記の文体も決めておく。
- **出版社のフォーマットは、見出しタグと章の定型に分けて書く。** 見出しの記号(例: `# ★` `## ●`)と、章の中の決まった並び(例: 章タイトル → リード → 結論 → 本論 → まとめ)は別の規則である。
- **lint の除外表は、最初は空でよい。** 最初の `audit` で定型行による誤検知が出たら、その行の形を足していく(`exclusions.md` 6節)。
- **記事の場合**は、構成の型を fujiwo-style 4節の型A〜C(技術解説、ニュース、イベントレポート)から選んで書く。書籍の章なら型Dである。自己言及の語(「本書」「本記事」など)と自称(「筆者」「私」)も決める(裁定 #4)。
- **本人の声の正例**(自筆メモ、過去の公開記事など)の場所を書いておく。「人が書いた感じ」の判断は、この正例に戻って行う。

プロファイルは、スキルがどの項目を読むかに合わせて節を切ってある。節の番号や見出しを変えてもスキルは読めるが、ひな形の節立てに合わせておくと、他のプロジェクトとの比較やレビューがしやすい。

## 5. 指示ファイルからプロファイルを指す

スキルは、依頼者が指定したファイル → 指示ファイルが指すファイル → ルートの `執筆プロファイル.md` の順にプロファイルを探す(`../SKILL.md` 0節)。ルートに置けば指示ファイルなしでも見つかるが、エージェントが原稿を扱うたびに入口のスキルを読むよう、指示ファイルにも次の2点を書いておく。

- 原稿のフォルダーに日本語の文章を書くときは、`fujiwo-manuscript-voice` を入口として読むこと
- 原稿のプロジェクト固有の約束事は `執筆プロファイル.md` に定めていること

指示ファイルの例: Claude Code なら `CLAUDE.md`、GitHub Copilot なら `.github/copilot-instructions.md`。

リンクの書き方や画像の置き場所など、スキルを使わない作業でも守ってほしい規則は、指示ファイルにも書いてよい。その場合は、どちらを正とするかを両方に書き、変えるときは正の側から直す(二か所に同じ規則があると、片方だけが古くなりやすい)。

## 6. 動作を確かめる

1. 既存の原稿が1本あれば、`audit` モードで診断する(例: `/fujiwo-manuscript-voice audit quick <原稿ファイル>`)。
2. 報告に、プロファイルを見つけた経路と、足りなかった項目が書かれているかを見る(`../SKILL.md` 3-7節)。「プロファイルが見つからなかった」と出たら、置き場所と指示ファイルの記述を見直す。
3. 定型行による誤検知が出ていたら、プロファイルの除外表に足す。
4. 文体の基調・自称・見出しタグの判定が、プロファイルの指定どおりになっているかを見る。
5. 一節相当の短いコピーで `revise` を試し、修正前後の主張・比重・言い切りの強さ・文の働きと、見出し・定型・術語の保持を確認する(`yomiyasu-integration.md` 5節)。原稿全体を一律に直さない。
6. 問題がなければ、`revise` や `write` で使い始める。

既存の原稿がない新しいプロジェクトでは、短い原稿を1本 `write` で書かせ、同じ点を確かめる。

## 7. 導入後の運用

- **プロジェクト固有の約束事はプロファイルに書く。** スキル本体に書き足さない(`../SKILL.md` 4節)。スキルを直すのは、どのプロジェクトにも共通する改善のときだけにする。
- **スキルを更新するときは、6つをまとめて配布元からコピーし直す。** 裁定表(`conflict-resolutions.md`)とチェックリスト(`manuscript-checklist.md`)は、中核4スキルと補助スキルの記述を前提にしているので、一部のスキルだけを新しくすると食い違う。
- **裁定表にない衝突に出会ったら**、スキルの報告に従って裁定案を記録し、どのプロジェクトにも当てはまるものは配布元のスキルに反映する。そのプロジェクトだけの事情なら、プロファイルに書く。
- **プロファイルの記入例**として、配布元のリポジトリ(『サステナブルコード』)の `執筆プロファイル.md` を参考にしてよい。出版社のフォーマット、敬体基調、lint の除外表まで記入した例になっている。
