# yomiyasu の原稿への適用

`yomiyasu` は、既存工程の読みやすさレビューと意味保持の比較に使う補助スキルである。独立した改稿工程や禁止語リストは追加しない。適用する規則は [裁定表](conflict-resolutions.md) #22〜#29 に従う。

## 1. モードと比較基準

| モード | 使い方 | 比較基準 |
|---|---|---|
| `revise` | 問題箇所を局所的に直し、修正前後を比較する | 読みやすさだけなら作業開始時の本文。内容変更が著者承認済みなら、その内容を反映した本文 |
| `write` | 提供素材と草稿の主張・条件・強さを照合する | 依頼と提供素材。元の原稿がない場合、比較用の「原文」は創作しない |
| `audit` | 読みやすさの問題と、意味が変わりうる修正案を診断する | 現在の本文。本文の書き換え・保存し直し・補助diffは行わない |

`revise` では編集前に比較用コピーを作る。既存ファイルを上書きしない、作業専用の一時領域を使う。著者承認済みの内容変更を基準にする場合は、その変更を読みやすさの修正と区別して記録する。

## 2. 読みやすさレビュー

主述・修飾・接続の問題を具体的に特定してから、問題箇所の近くに修正を絞る。語の言い換えだけでなく、条件・否定・因果・主体と対象の関係を修正前後で確認する。

- 自然なシステム動作、定義された術語、定着した慣用句、著者の軽口は残す。
- 読者が追うために必要な反復は残す。文長や装飾の数値だけで整形しない。
- 不明な関係は本文で確定せず、原文を残して確認事項にする。未知の主体・原因・条件は足さない。
- 指摘は既存の台帳に統合する。同じ箇所・同じ問題への重複指摘は一件にまとめ、異なる問題は分ける。

## 3. 補助スクリプト

配置先にある `yomiyasu` の `scripts/` を使う。以下はリポジトリのルートからの PowerShell の例であり、`<skills>` は実際のスキルディレクトリに読み替える。bash では `$env:PYTHONUTF8=1` を `export PYTHONUTF8=1` に、`\` を `/` に替える。`$target` は対象本文、`$before` は比較基準のコピーの絶対パスを事前に設定する。

### 補助lint

`full` と、`write` / `revise` で原稿を保存したときに実行する。`audit quick` は既存lintと目視検査を行い、補助lintは必要な場合だけ追加する。

```powershell
$env:PYTHONUTF8=1
python <skills>\yomiyasu\scripts\yomiyasu_lint.py --json $target
```

既存の natural-japanese のlintを置き換えない。候補は台帳で「直す/残す」を判断し、`--strict` による警告ゼロを合否基準にしない。太字の表示を指摘された場合は、実際の表示先で確認してから直す。確認できない場合は自動適用せず、その旨を報告する。

### 補助diff

`revise` で修正案がまとまったら、比較基準と修正後の本文を一度比べる。`write` では提供素材との対応を目視で確認し、元の本文が提供されている場合だけ補助diffを使う。

```powershell
$env:PYTHONUTF8=1
python <skills>\yomiyasu\scripts\yomiyasu_diff.py $before $target --json
```

主たる立場が明確な場合だけ `--stance=勧め`、`--stance=決まり`、`--stance=説明` を追加する。説明と助言が混在する章で、各文を同じ働きにそろえるために指定してはいけない。判定できなければ省略する。

スクリプトは情報増減や文の働きが変わった疑いを示すだけで、意味の等価性を保証しない。候補を目視で確認し、**主張・比重・言い切りの強さ・文の働き**と、条件・否定・因果・時系列の範囲を比べる。候補がなくても、この比較は省略しない。

## 4. 収束・出力・後片付け

全体の収束は既存の natural-japanese の工程が管理する。補助lintによる同じ問題の修正試行は最大2回、補助diffからの修正は1回とし、警告を消すためだけの再実行・往復修正はしない。その後の意味保持は目視で確認する。同じ指摘が2周連続で再発した場合は発散ガードを適用し、原文を残すか、内容の確認が必要なら著者に確認する。

原稿には本文だけを反映し、`yomiyasu` の「変えたところ」「書き手に確かめたい点」などの出力欄は追加しない。理由と確認事項は既存の台帳・最終報告に統合する。対話で確認が必要な場合も、利用環境の質問手段に従い、一度に一件を尋ねる。

完了時は今回作成した比較用コピー・JSON・台帳を削除する。元の原稿や利用者が用意した資料は削除しない。比較基準、主な修正、残した理由、未確認事項を報告する。

## 5. 導入時の検証例

まず一節相当の短い検証用本文で試し、原稿全体へ一律に適用しない。例えば次の文は、見直す箇所と残す箇所を区別するために使える。

> 筆者は、入力が不正な場合に値を代入しない処理を選びました。このツールはログを集めます。契約は、操作の前提条件と事後条件を定めます。重要なのは、失敗しても状態を変えないことです。

この例は引用形式の検証データであり、実際の引用原稿を書き換える指示ではない。「重要なのは」を整える場合も評価を残す。「値を代入しない」を「falseを代入する」へ変えず、自然なツール主語と術語の「契約」を保つ。さらに見出し・初出の用語太字・注記・引用・コードを添え、それらがプロファイルどおりに保護されるか確認する。
